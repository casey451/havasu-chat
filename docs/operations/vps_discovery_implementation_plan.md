## 1. Fit assessment, workstream by workstream

### A. Local-LLM category validation — **goal: GO. Mechanism: NO-GO.**

The fear is real and the codebase confirms it: categorization is **deterministic
substring matching, no LLM anywhere** (`app/categories/subcategories.py` —
`derive_subcategory()` walks Google type tokens → `_TYPE_TO_SUBCAT` (~90 entries) →
`SUBCATEGORY_TO_PRIMARY` → 13 canonical slugs; unmatched rows get `None` and fall into
"All"). Multi-source ingest (Google Places, OSM, GoLakeHavasu partners, NPI, PDGA)
merges through `app/contrib/ingest_reconciler.py` with no semantic check that the
resulting category is sane. A roving validator is the single highest-value
data-quality idea in the brief.

But the local-model mechanism fails on this box and on the economics:

- 4 vCPU, no GPU. A quantized 7–8B model manages a few tokens/sec; fine for a slow
  patrol in theory, but it's a new service to install, version, eval, and babysit.
- The thing it saves is API spend that rounds to **~$1–2/month**: a full-catalog
  patrol with `gpt-4o-mini` (rules + item ≈ 500 tokens in, ~20 out) costs roughly
  $0.10–0.30 per thousand items. The existing plan already killed local embeddings
  over $0.02/month; the same logic kills a local classifier over $1/month.

**Recommended cut:** keep the *exact* architecture from the brief — Claude-authored
per-category rulesets, mechanical application, confidence scores, human review queue —
but apply rules with `gpt-4o-mini` batch calls from a scheduled job:

- **Rulesets as versioned artifacts:** yes, clean fit. Store under
  `prompts/category_rules/<primary>.md` (or `.json`), regenerated by Claude offline,
  reviewed in PR like any prompt. They sit beside the existing `prompts/` convention.
- **Per-item flag without touching serving:** add nullable `category_confidence`
  (float) + `category_flagged_at` on `Provider` (additive migration, serving path
  never reads them) — mirrors the existing `liveness_score` pattern exactly.
- **Review surface:** don't build one. Route flags into the existing admin queue
  family (`/admin/providers/pending` pattern, `app/admin/provider_approval.py`) as a
  new "miscategorized?" list. The approve/reject plumbing already exists.
- **Scheduling:** a weekly GitHub Actions workflow alongside the six existing scrape
  workflows. Hourly sampling is over-engineering for a catalog this size.

**Touches:** new script `scripts/category_patrol.py`, one additive migration, one admin
list view, one workflow file. **Effort:** M (2–4 days). **Prod-write rule applies:**
patrol writes flags to prod rows → dry-run → counts → approval, per CLAUDE.md.

### B. Tier-3 → intent-catalog feedback loop — **GO; the logging half already exists.**

Everything needed is already persisted: `chat_logs` records `tier_used` ('1'|'2'|'3'|
'gap_template'|…), `normalized_query`, `mode`, `sub_intent`, `entity_matched`, token
counts (`app/db/models.py:284+`, written by `app/db/chat_logging.py:log_unified_route`).
There is also a privacy-friendly `query_log` aggregate. Nothing to instrument.

What's missing is only the batch half: a script that pulls tier-3 (and `gap_template`)
rows, embeds `normalized_query` (`text-embedding-3-small`, ~$0.001/run), clusters, and
emits a ranked gap report. Important codebase reality: **intents are code, not data** —
`tier1_templates.py` regexes, `intents/resolver.py`, `intents/dicts.py`. So "Claude
drafts candidate intents" lands as **draft PRs / report sections a human reviews and
merges**, which matches the existing workflow exactly. No new approval machinery.

Caveat: pre-launch, tier-3 traffic is dev noise. Build the script thin (one file, one
workflow, report artifact to `relay/` or a gist), and let it earn complexity after
launch. Also note `USE_INTENT_LAYER` defaults **off** in prod
(`app/chat/intents/runtime.py:5-6`) — enabling it is itself probably the single biggest
tier-3-shrinking lever, and it's already built.

**Touches:** `scripts/tier3_gap_report.py`, one workflow. **Effort:** S–M (1–2 days).

### C. Local vector search — **GO on the feature, NO on the VPS service.**

Embeddings already exist: `providers.embedding`, `events.embedding`,
`programs.embedding` (JSON columns, populated at ingest by `app/core/extraction.py`),
plus the semantic LLM cache (`app/chat/llm_cache.py`, cosine in Python over ≤200 rows).
The catalog is small (low thousands of rows); brute-force cosine in-process is
comfortably sub-50ms with no new infrastructure, no network hop, no second failure
domain. A VPS vector service would be strictly worse than what a 30-line in-app
function gives.

Prerequisite hygiene before shipping "more like this": fix the **dimension
fragmentation** (1536 real vs 32-dim deterministic fallback, `extraction.py:295`) and
add a backfill for rows with NULL embeddings. Then it's an endpoint + a card-row UI.
pgvector on Railway Postgres is the upgrade path if the catalog ever grows past
brute-force; not needed now.

**Touches:** `app/core/extraction.py` fallback fix, backfill script, one route + small
similarity module, template tweak. **Effort:** M (2–3 days incl. backfill rehearsal).

### D. Session-aware caching — **mostly already built; the real item is the hint extractor.**

`app/core/session.py` already keeps per-session slots, `onboarding_hints`,
`prior_entity` pronoun resolution (3-turn freshness), and last-result-set dedup —
strictly session-scoped, in-memory. The brief's ask exists.

What the brief's instinct is actually pointing at is the **hint extractor**:
`extract_hints()` fires synchronously on **every turn** (`unified_router.py:868`),
adding ~1s latency and ~90% of projected API spend at target scale — including on
turns that resolve as zero-token Tier-1 regex lookups. The fix (regex pre-gate, only
call the LLM when a hint pattern is plausible; cache per session; or move async) was
already flagged in `vps_workload_plan.md §2` as worth more than every VPS workload
combined. This is the highest-ROI single change in the entire brief and it's pure code.

**Touches:** `app/chat/hint_extractor.py`, `unified_router.py:868`, tests.
**Effort:** S–M (1–2 days incl. careful tests — it's on the serving path).

### E. Async background job queue — **already decided; don't rebuild it.**

`background_job_infrastructure_decision.md` locked Option A: GitHub Actions / Railway
cron for scheduled work, `BackgroundTasks` + retry wrapper (`app/core/background.py`,
shipped) + Outbox (shipped for magic-link) for event-triggered work. Six scheduled
workflows already run on Actions for free. A VPS-hosted queue/worker would be a third
job substrate contradicting a standing decision, with no triggering condition met
(Phase 4 of the VPS plan defines the triggers: Actions minutes exhausted, >6 GB RAM
job, stable-egress-IP need). Every workstream in this plan fits the existing pattern.

**Effort:** zero — by design.

### F. Lightweight provider/place enrichment — **lanes largely exist; new scrape lanes stay individually HALT-gated.**

The brief under-counts what's built: GoLakeHavasu Trumba/iCal events + partners
(sanctioned aggregator lanes, exactly what the brief prefers), parks-rec WebTrac, OSM
Overpass, NPI/AZ-ROC/BBB verification scripts, gas prices — all reconciled through
`ingest_reconciler.py` (place-id → 50m geo+name → ambiguous) with source-priority
merge. There is no general infrastructure left to build; "F" reduces to *which new
sources*, one decision at a time.

The risky direction is already on file: `docs/scraper/openclaw_facebook_avenues.md`.
**Recommendation: each new scrape lane gets its own explicit ToS risk review and Casey
approval before any code** — Facebook/Meta surfaces in particular default to NO
(ToS-hostile, brittle, and the existing aggregator lanes cover most of the event gap).
Local business *websites* (plain HTML, robots-respecting, low volume) are the
defensible end of the spectrum if a concrete field gap justifies them. The VPS's only
legitimate role here is Phase-4-trigger territory (stable egress IP), not now.

**Effort:** N/A as infra; S–M per approved lane.

### G. Community feedback loop — **backend exists end-to-end; this is a UI affordance.**

Chat already classifies `contribute` and `correct` modes with zero-token intake
templates (`unified_router.py:636,651`), feeding the `contributions` queue
(`app/db/models.py:471+`, status pending/approved/rejected/needs_info) and
`FieldHistory` claims with confirm/dispute states. `chat_logs.feedback_signal` exists
and is unused. The whole "review queue on the VPS" is unnecessary — the queue is in
Postgres with admin surfaces shipped (`/admin/contributions`).

Remaining work is genuinely small: an "outdated?" / "missing something?" affordance on
provider cards and category pages that posts into the existing contribution queue, and
optionally wiring `feedback_signal` to a thumbs control in chat. Calm-texture compliant
as long as it stays a quiet link, not a prompt.

**Touches:** templates + one POST route reusing `contribution_store`. **Effort:** S (≤1 day).

### H. Seasonal heuristics — **mostly built; one real gap. GO as a small code task.**

More exists than the brief assumes: `SeasonalHours` + `Entity.seasonal_hours` are
populated schema, `effective_seasonal_hours()` (`app/providers/queries.py:115`) is
live on provider detail views (`view_models.py:191`), the home snowbird panel, and a
Phase-7 snowbird chat query (`app/chat/snowbird_query.py`, Oct 1–Apr 30 window locked
2026-05-20). `Entity.heat_exposure` exists from Phase 3.1.

The genuine gap: **tier-2 open-now filtering ignores seasonal overlays** — it uses
`effective_hours_structured()` (`queries.py:355`), which reads weekly hours only. So a
provider on summer hours can be reported open at its winter schedule in chat. Work:
apply the seasonal overlay inside that one path (+ tests), then optionally a seasonal
prominence nudge. The larger half of total effort is operator curation — populating
seasonal rows for the providers that actually swing.

**Touches:** `app/providers/queries.py:effective_hours_structured` (or a seasonal-aware
wrapper used by `tier2_db_query.py`), tests, curation pass. **Effort:** S–M (1–2 days
code; curation ongoing).

### I. Data-freshness monitoring — **half exists; close the heartbeat gap. GO.**

Per-row freshness is well covered (`last_verified_at`, `scraped_at`,
`newest_review_at`, `liveness_score`, `confidence_tier.py` hedging bands, weekly
cross-source dedup audit workflow). The real gap matches the brief: **nothing notices
a silently dead pipeline** — if River Scene's workflow starts returning 0 events,
nobody is paged.

Minimal cut: a daily check (one more Actions workflow, or a step appended to each
scrape workflow) that asserts `max(scraped_at)` / row-delta per source against
expected cadence and fails loudly (Actions failure email is already a notification
channel; Sentry breadcrumb optional). An `ingest_runs` heartbeat table is the V2 if
the simple query proves noisy.

**Touches:** `scripts/freshness_check.py`, one workflow. **Effort:** S (≤1 day).

### J. SMS shortcuts — **correctly sequenced as later; nothing to pre-build.**

Schema anticipates SMS (`AlertSubscription.delivery_channel` allows 'sms') but there
is no Twilio code anywhere. The brief's premise ("pre-bake responses so keywords skip
the API") is already satisfied by architecture: Tier-1/Tier-2 answers are zero-token
and fast — an SMS lane is a Twilio webhook in front of `unified_router` plus
SMS-length formatting, not a caching project. Keep it sequenced after the intent layer
is enabled and validated (which also maximizes the zero-token hit rate SMS depends
on). No VPS role.

**Effort when its turn comes:** M.

### K. Local fallback / reliability layer — **defer; take the staging mirror instead.**

A true warm standby needs data replication, DNS failover, and drift management — a
real ops surface for a single-founder, pre-launch product, protecting against outages
(Railway + OpenAI simultaneously) that degrade a product with, today, dev traffic.
The already-planned staging mirror (VPS plan Phases 1–2) builds 80% of the bones
(compose stack, restored backups, rehearsed migrations); if launch-scale reality later
justifies failover, promote from there. Don't build it now.

## 2. Phased plan (HALT checkpoints, approval gate before each merge)

Sequencing principle: serving-path wins and data-quality first; loops second;
discovery polish third; everything trigger-gated last. Each phase = one feature
branch + PR per item, `pytest -q` + `ruff check .` green, Casey merges. Prod data
writes always dry-run → counts → approval.

**Pre-existing track (unchanged):** `vps_workload_plan.md` Gates A–C — staging mirror,
prod-shaped data, load test. Proceeds independently; it is the only VPS work in this
plan. VPS hygiene (SSH password auth off, UFW) should land before anything new runs
on that box.

### HALT 1 — Serving path + catalog quality (the high-ROI core)
1. **Hint-extractor gate/cache/async fix (D)** — biggest cost + latency win in the
   brief; pre-launch priority per the existing plan.
2. **Category patrol v1 (A, gpt-4o-mini cut)** — rulesets in `prompts/category_rules/`,
   additive confidence/flag columns, flags into existing admin queue, weekly workflow.
3. **Freshness heartbeat (I)** — daily staleness check + loud failure.

*Gate: approve the hint-extractor behavior change (serving path), the additive
migration, and the patrol's first prod write after a dry-run count review.*

### HALT 2 — Feedback loops
4. **Tier-3 gap report (B)** — clustering script + workflow; output = ranked report,
   Claude drafts intent candidates as PR material.
5. **Community feedback affordances (G)** — "outdated?/missing?" into the existing
   contribution queue; optionally wire `feedback_signal`.
6. **Decision point (not code): enable `USE_INTENT_LAYER` in prod** after the gap
   report confirms coverage — the cheapest tier-3 reduction available.

*Gate: approve UI copy (calm-texture check) and the flag flip.*

### HALT 3 — Discovery & seasonality
7. **Embedding hygiene + "more like this" (C)** — fix 32/1536 fallback, backfill,
   in-app similarity endpoint + card row.
8. **Seasonal open-now fix (H)** — make tier-2 open-now seasonal-aware; prominence
   nudge second; schedule the curation pass separately.

*Gate: approve backfill run (prod write) and ranking-nudge behavior.*

### HALT 4 — Trigger-gated (no default build)
- **SMS lane (J):** after intent layer is on and a Twilio/928 decision is made.
- **New scrape lanes (F):** one ToS risk review per source; Meta surfaces default NO.
- **Fallback layer (K):** only if post-launch reality demands it; grow from staging.
- **Local LLM (A-mechanism):** revisit only if patrol API spend exceeds ~$20/mo —
  same threshold logic as the embedding no-go.

## 3. Dependencies & shared infra

- **No new job substrate.** Everything schedules as GitHub Actions workflows beside
  the six existing ones (Option A memo). The "job queue first" instinct in the brief
  is already satisfied.
- **Ruleset/artifact convention** (HALT 1, item 2) is the one genuinely shared new
  piece: `prompts/category_rules/` versioned in git, regenerable by Claude, reviewed
  by PR. The tier-3 gap report (B) reuses the same convention for its prompt.
- **Admin queue reuse**: A and G both route into existing review surfaces; build no
  new review app.
- **Embedding hygiene (C-prereq)** should land before any new feature depends on the
  vectors; it also benefits the existing LLM cache.
- **Staging mirror (separate track)** becomes the rehearsal venue for every migration
  and backfill in HALTs 1–3 once VPS plan Phase 2 lands — a strong reason to let
  Gate A proceed first or in parallel.

## 4. Risk callouts

- **ToS (F):** standing posture — per-lane explicit approval; prefer the existing
  sanctioned aggregator lanes; Meta surfaces default NO. Already flagged twice in
  repo docs; treat as settled unless Casey reopens it.
- **Serving path (D fix, H ranking, C endpoint):** the hint-extractor change alters
  every-turn behavior — needs the existing router test suite extended before merge;
  ranking nudges need a before/after sample review to honor calm texture (quietly
  more correct, never louder).
- **Prod writes (A flags, C backfill, H curation):** all follow dry-run → counts →
  approval, per CLAUDE.md. Patrol writes only to new nullable columns, so worst-case
  blast radius is a wrong flag, never a wrong listing.
- **VPS security (existing plan §1.1):** password SSH + no firewall — must be fixed
  at Gate A before the box hosts anything that touches prod-shaped data.
- **Pre-launch signal scarcity (B):** clustering dev traffic can manufacture fake
  gaps; treat pre-launch reports as smoke tests of the pipeline, not roadmap input.
